Conversations, Not Forms

Alumni Connect replaces traditional search interfaces with a natural language AI chatbot. Instead of filling out filter forms, users simply ask: "Find me alumni who are doctors in Chennai." The AI handles the rest — parsing intent, querying the graph database, and returning personalized results.

Privacy-First, Admin-Gated

Every profile goes through a conversational onboarding and requires admin approval before becoming visible. This ensures only verified alumni can search and connect — building institutional trust and keeping data quality high from day one.

Workflow Detail

Conversational Onboarding — Step by Step

Login

User opens the app and signs in

Enters mobile number (with country code picker) or email. Backend creates user record with pending_approval status if new. JWT tokens issued and stored in AsyncStorage.

API: POST /api/auth/login — returns access_token, refresh_token, is_new_user flag
WebSocket Connect

AI Chat WebSocket opens, auto-greet triggers

WebSocket connects to /ws/ai-chat. First message sends JWT for authentication. Based on user status (new vs. returning, onboarding step), the agent sends an appropriate greeting and begins onboarding.

Cache check: Redis onboarding:{user_id} loaded first, fallback to Postgres onboarding_data JSONB column
Structured Collection

Agent asks profile questions one-by-one

The onboarding sub-agent uses structured output (Pydantic OnboardingResponse) with actions: ask, save, confirm, create_profile. Each response is validated by the OnboardingRuler before saving.

Fields: name, completed_12th, highest_grade, academic_year, gender, age/DOB, city, country, profession, interests, activities
Stateful Caching

Each answer saved to Redis with 7-day TTL

Every field answer is immediately cached in Redis at onboarding:{user_id}. On disconnect, partial data flushes to Postgres onboarding_data JSONB. On reconnect, data restores from Postgres back to Redis.

Key insight: Users can close the app mid-onboarding and resume exactly where they left off — no data lost
Profile Creation

All fields collected → Profile created across databases

User record updated in PostgreSQL with full profile. Graph nodes and relationships created in Neo4j (Alumni → City, Profession, Interests, Activities). A profile narrative is generated by the LLM and converted to a vector embedding (pgvector).

Approval Gate

Status remains pending_approval until admin acts

User sees an "Under Review" screen. Can check status via a refresh button. Admin sees the pending user in the admin dashboard with approve/reject options. Rejection includes an optional reason displayed to the user.

Workflow Detail

Search & Connect — Step by Step

Natural Language Search

User asks the chatbot to find alumni

The Router node classifies intent as "search" and hands off to the Search Agent — a ReAct agent with access to graph query tools. Examples: "doctors in Mumbai", "alumni who play cricket", "female engineers from 2018 batch".

Graph Query Execution

Agent selects and executes appropriate tools

Three search tools available:

  • search_alumni — structured Cypher query with filters (city, profession, interests)
  • search_alumni_by_cypher — custom Cypher for complex queries
  • find_alumni_with_shared_interests — similarity-based matching
Database: Neo4j graph traversal — Alumni → City, Profession, Interest, Activity relationships
Results Displayed

Profile cards rendered inline in the chat

Search results return as ProfileCard components inside the chat bubble, showing name, profession, city, graduation year, interests, and a Connect button for each match.

Connection Request

User says "connect me with [name]"

The Connect Handler uses structured output to parse which alumni the user wants to connect with. Creates a connection record in PostgreSQL and a CONNECTED_TO relationship in Neo4j with pending status.

Status flow: pending → accepted or declined
Connections List

Accepted connections visible in Connections tab

The Connections screen shows all accepted connections with real-time online/offline status via Redis presence tracking. Each connection is tappable to open a private chat.

Presence: Redis key presence:{user_id} with 60s TTL, refreshed by heartbeat
Private Chat

Real-time 1-on-1 messaging

Dedicated WebSocket at /ws/private-chat with active connection registry for instant delivery. Messages stored in MongoDB with read receipts. Supports chat history loading on connection open.

AI Agent Architecture

LangGraph Agent — The Brain of the System

Every user message flows through a LangGraph state machine that classifies intent and routes to specialized sub-agents. Each sub-agent has its own tools, prompts, and structured output schemas.

🧭 Router Node

  • 1
    Receives every user message with conversation history
  • 2
    LLM classifies intent into one of 5 flows
  • 3
    Routes to the appropriate sub-agent with full context
  • 4
    State machine tracks current_flow across turns

📝 Onboarding Sub-Agent

  • 1
    Structured output via Pydantic OnboardingResponse
  • 2
    Actions: ask, save, confirm, create_profile
  • 3
    Field validation via OnboardingRuler
  • 4
    Generates profile narrative + vector embedding on completion

🔍 Search Sub-Agent (ReAct)

  • 1
    ReAct pattern with tool calling via LangChain
  • 2
    Tools: search_alumni, search_by_cypher, find_shared_interests
  • 3
    Queries Neo4j graph for structured results
  • 4
    Returns formatted profile cards for inline rendering
💡
LLM Provider Abstraction
The agent system supports both OpenAI and Ollama as LLM providers via a single config switch. Embedding models similarly abstracted — OpenAI (1536-dim) or Ollama/nomic-embed-text (768-dim). Switch between cloud and local inference without code changes.

What Makes It Different

Key Design Decisions

🕸️

Neo4j Graph for Relationship Queries

Alumni relationships are inherently graph-shaped. A graph database enables queries like "find alumni who share 3+ interests with me" or "alumni connected to my connections" that would be extremely complex in SQL. Cypher queries traverse relationships naturally.

Alumni
→
City
←
Alumni
→
Interest
🧠

Dual Search: Graph + Vector Embeddings

Structured queries go through Neo4j for precise filtering. Semantic/fuzzy queries use pgvector embeddings (768-dim) generated from LLM-written profile narratives. This hybrid approach handles both "doctors in Mumbai" and "people like me" queries.

User Query
→
Agent Decides
→
Neo4j or pgvector
💾

Redis → Postgres Onboarding Cache

Onboarding data lives in Redis (7-day TTL) for fast read/write during conversation. On disconnect, it flushes to Postgres JSONB. On reconnect, it restores. This two-tier approach ensures zero data loss while keeping the chat responsive.

🔄

LLM Provider Abstraction

A single config switch (LLM_PROVIDER) toggles between OpenAI (cloud, GPT-4) and Ollama (local inference). Embedding models similarly abstracted. Develop locally with Ollama, deploy with OpenAI — zero code changes.
