Workflow Detail

Driver Journey — Step by Step

Login & Dashboard

Driver opens the app

Sees active trips, completed trip history, and a demand summary showing how many passengers are requesting rides per route and time slot.

Create Trip

Selects route, direction, and departure time

Sees aggregated ride requests per time slot to make informed decisions about when to depart. Sets initial seat capacity.

API: POST /trips — driverId pulled from JWT, not user input
Active Trip

Trip enters "boarding" then "in_progress"

GPS tracking begins automatically — collecting position every 10 seconds, batch uploading every 30 seconds. Driver taps the next stop in the horizontal stop tracker to advance.

Geofencing: When within 500m of a stop (Haversine calc), the system auto-updates currentStopId
Passenger Count

Uses +/- buttons to track passengers

As passengers board and alight at each stop, the driver taps +/- to update the count. A 1.5-second debounce batches rapid taps into a single API call.

Key insight: This count is the source of truth for seat availability, not bookings. Bookings serve as demand signals.
Stop Events Logged

Every stop generates analytics events

The system automatically logs arrival, departure, and count_update events at each stop with passenger snapshots. This builds the analytics dataset.

Metrics: Dwell time, boarding/alighting counts, inter-stop travel time, occupancy per segment
Trip Complete

Driver ends the trip

Final departure event logged with all remaining passengers alighting. Trip status → completed. All bookings auto-completed. Trip moves to history.

Workflow Detail

Passenger Journey — Step by Step

Discover Routes

Browse available routes

The home screen shows route cards with origin-destination pairs. If the passenger has an active booking, a prominent banner shows tracking status.

Find Trips

See available trips on a route

Lists upcoming trips with departure times, driver info, vehicle type, and real-time seat availability (remaining seats calculated from driver's count).

API: GET /routes/:routeId/trips — returns trips with seat counts
Book Seats

Select boarding stop, drop stop, and seats

Picks where to get on and off. Can book multiple seats (e.g. for family). Booking functions as a demand signal — the driver sees demand ahead.

Status flow: requested → confirmed → boarded → completed
Live Tracking

Track the vehicle in real-time

Once booked, the passenger sees a live tracking screen with:

  • Horizontal stop progress bar (auto-scrolls to current stop)
  • Passenger status: waiting → boarded → arrived
  • Seat availability in real-time
Tech: WebSocket (WS /ws/trip/:tripId) with automatic fallback to REST polling every 15s if WebSocket fails
No Trips? Request a Ride

Signal demand when no trips are available

Passengers can post ride requests with preferred time slots. These aggregate on the driver's dashboard as demand signals, incentivizing drivers to create trips where demand exists.

Expiry: Ride requests auto-expire after 4 hours. Drivers see demand grouped by route and time slot.

Connectivity Handling

Designed for Any Network Condition

LT Ride is built for the real world — where networks range from fast 4G/5G in urban areas to slow, intermittent 2G in remote regions. The architecture ensures zero data loss and graceful degradation regardless of connectivity.

📶 Good Connectivity (3G/4G/5G)

  • 1
    GPS uploads in real-time batches every 30 seconds
  • 2
    WebSocket connection provides instant position updates to passengers
  • 3
    Passenger counter changes sync with 1.5s debounce
  • 4
    All features work at full fidelity

📱 Slow Network (2G / Patchy)

  • 1
    GPS still collects locally every 10 seconds regardless of network
  • 2
    Batch uploads attempt every 30s — if they fail, data queues in IndexedDB
  • 3
    Passenger app falls back to REST polling (every 15s) when WebSocket drops
  • 4
    Routes cached locally for offline browsing and trip creation

🚫 No Connectivity

  • 1
    GPS collection continues uninterrupted in the background
  • 2
    All location batches queue in IndexedDB with auto-incrementing keys
  • 3
    Driver can still navigate stops using cached route data
  • 4
    On reconnect: queued batches auto-flush in order — server receives complete GPS trail
💡
Key Design Principle
GPS data collection and network sync are completely decoupled. The device always collects. The network layer handles delivery when possible. This two-layer approach ensures no trip data is ever lost, regardless of network conditions.

What Makes It Different

Key Design Decisions

📊

Bookings = Demand Signals, Not Reservations

Unlike ride-hail apps, bookings here are demand forecasts. The driver's +/- passenger counter is the sole source of truth. This matches how informal mass transport actually works — flexible, organic, and driver-controlled.

Passenger Books
→
Signal Created
→
Driver Sees Demand
→
+/- = Truth
🎯

Geofence-Triggered Stop Advancement

The backend runs Haversine distance calculation on every GPS batch. When the vehicle enters a 500m radius of a stop, the system auto-updates the current stop. Reduces driver distraction while keeping tracking accurate.

GPS Batch In
→
Haversine Calc
→
< 500m?
→
Auto-Update Stop
📐

Debounced Passenger Counting

The +/- button uses a 1.5-second debounce. Rapid taps (e.g. 5 passengers boarding quickly) collapse into a single API call. This prevents flooding the server while keeping the count accurate — essential on slow networks.

🔗

Monorepo with End-to-End Type Safety

A shared TypeScript package (@local-transport/shared) defines all types and constants used by both apps and the backend. If a Trip type changes, all three packages see it at compile time. Zero type drift.
